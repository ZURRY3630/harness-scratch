01

定位与全景

MiniHarness 是《智能体 Harness 工程指南》的配套实战项目：一个最小但闭环完整的 Agent Harness。它覆盖了 Harness 最核心的一条链路——模型调用 → 工具登记 → 权限审批 → 工具执行 → 结果回填 → 继续推理——并以 Streamlit 提供带人工审批面板的 Web UI。

本次评估的核心判断：审批挂起/恢复的骨架搭对了，这是 Harness 里最难做对的机制之一；但执行链路没有任何安全收口（校验、沙箱、超时、审计全部缺失），距离生产级差四个量级的能力——安全收口、持久化恢复、可观测性、编排与生态。

02

现状架构

五层结构：接入层（两个入口）→ 运行时引擎 → 能力层（工具 + 权限）→ 模型层 / 记忆层 → 核心数据结构。依赖方向清晰单向向下，无循环引用。

◈Agent Loop 执行循环

关键设计 · 审批挂起与恢复

模型返回的 tool_calls 只写入 memory（登记），回到循环开头由 get_pending_tool_calls() 统一对账裁决。ASK 时引擎 yield "[APPROVAL_REQUIRED] {json}" 并 return——工具调用留在 memory 里等下一轮对账；用户批准后 UI 调 approve(call_id)，引擎不带 user_input 续跑即可无缝恢复。拒绝则写入 [DENIED] tool 结果。挂起/恢复不丢状态，因为状态全在消息账本里。

04

关键机制

4.1权限模型：声明的五级，实际的三种

PermissionLevel 声明 vs decide() 实际行为
声明级别实际行为差距
FULL_TRUST直接 ALLOW符合声明
ASK_FIRST首次 ASK，批准后该 call_id ALLOW符合声明
AUTO_WITH_NOTIFICATION与 ASK_FIRST 完全相同无"自动 + 通知"行为
APPROVE_ALWAYS与 ASK_FIRST 完全相同无"记住批准"语义
MANUAL_ONLY直接 DENY语义错位：应转人工而非拒绝

批准是 call_id 粒度的一次性白名单（approved_call_ids: Set[str]），没有工具级 / 参数级的规则记忆，也没有持久化。

4.2工具执行：双路径、零校验

存在两个几乎相同的执行原语——ToolRegistry.execute() 与 PermissionGate.execute()，引擎只调用后者，前者冗余。更关键的是：两者都没有调用 _validate_params（Schema 参数校验）与 _validate_path（目录边界校验）。白名单与路径沙箱的机制写了，但从未进入执行链路。当前工具执行 = 直接 func(**arguments)：模型幻觉出的未知参数抛 TypeError 被吞成错误字符串，越权路径无法拦截。

4.3事件协议：文本前缀行协议

引擎与 UI 之间用文本前缀约定三类事件：[APPROVAL_REQUIRED] {json} → 待审批队列；[Tool {name}] … → 工具日志；其余文本 → 最终回答。脆弱点：事件无类型 schema；UI 端 final_text 会被后一条覆盖；模型输出若恰好以这两个前缀开头会被误分类。

4.4做对了的细节：OpenAI 消息配对

  • assistant 带 tool_calls 且 content 为空时，完全省略 content 键而非传 null（源码注释明确标注这是关键）；
  • tool 消息必须带 tool_call_id，否则丢弃——避免孤儿 tool 消息触发 API 400；
  • 模型返回的 call_id 为空时用 uuid 兜底；参数 JSON 解析失败退 {}。

这些是实际踩坑后沉淀的兼容性处理，生产化时应原样保留进 Memory v2。

06

生产级目标架构

以指南五大原则为决策准绳——约束优先、可验证性、渐进信任、故障假设、智能体工效——并建议生产定位对齐 Claude Code 的任务型范式（按需启停 + 权限模式 + 可扩展工作流），而非 OpenClaw 的常驻自驱型，除非业务需要后台自主运行。

与现状的三点本质差异

执行收口——所有工具调用必经 Validator → Gate → Sandbox → Audit 单一链路，无旁路；状态外置——memory / 工作流状态落盘，进程可死可复活；平面解耦——模型、工具、记忆、权限各有接口契约，可独立替换。

6.1各子系统目标（摘要）

子系统 × 现状 → 目标
子系统现状目标

ToolExecutor双路径 · 零校验 · 阻塞执行单点流水线：查表 → Schema 强校验 → 路径边界 → 权限裁决 → 沙箱执行（超时 + 资源限制）→ 结果治理 → 审计落盘

6.2安全设计要点（指南第 12 章威胁模型）

  • 提示注入防护：工具结果按不可信数据处理——进 memory 前做围栏标记（包裹 + 来源角色声明），执行类工具对结果中的指令样文本告警。
  • 审批防篡改：审批对象带 call_id + 参数哈希，批准执行前校验参数未变。
  • 路径防护：resolve + is_relative_to 已有，补符号链接解析与 Windows 盘符 / UNC 逃逸防护。
  • 密钥卫生：.env 不入库；日志、审计、异常中自动脱敏 key 与敏感路径。
  • 审计日志：who（session）/ when / what（tool + 参数哈希）/ decision / 结果元数据，SQLite 起步。
07

验收清单

以"能上生产"为标准（对应指南第 13 章评估方法论），按优先级分四组基线。

P0 · 正确性与安全（上生产前必须）

  • 所有工具调用经过单一执行链路（校验 → 权限 → 沙箱 → 审计），无旁路
  • 参数 Schema 校验全量生效；路径类工具 100% 有目录边界
  • 工具执行有超时上限；模型调用有超时 + 重试；引擎异常不崩溃、可恢复
  • 权限五级语义与声明一致；审批可持久化、可审计；拒绝与转人工路径分离
  • 无调试输出泄漏（print 清零，密钥脱敏）
  • 轮次 / Token 预算耗尽行为确定：合法回填 + 明确终止事件

P1 · 可靠性与可运营

  • 会话与消息持久化；进程重启后可恢复进行中的任务
  • 结构化事件协议 + 流式输出
  • 上下文自动压缩，长会话不因 token 超限失败
  • OTel trace + 核心指标（turn 数 / token / 工具延迟与失败率 / 审批等待时长）+ 结构化日志
  • 配置全量生效 + 特性门控

P1 · 工程质量

  • 测试体系：工具层单测（校验 / 权限 / 沙箱）· 引擎 loop 集成测试（mock 模型）· 审批挂起/恢复端到端 · 回归集
  • 类型检查（pyright 已配置）+ lint + CI 门禁
  • 包正名、模块边界清晰、public API 有 docstring
  • 评估基线：固定任务集的端到端成功率 / 步数 / token 成本 benchmark，防止演进退化

P2 · 生态扩展（按业务需要）

  • MCP 客户端（stdio + HTTP），外部工具与本地工具同一安全链路
  • 任务编排 + 多智能体 Coordinator
  • 插件体系（工具包 / 子智能体 / 钩子三类扩展点）
  • 可写长期记忆

路线图与决策

M1安全收口

执行链路单点化 · Schema / 路径校验生效 · 工具超时 · print 清理 · 引擎异常兜底。
交付判据：问题清单 P0 #1–6 全部关闭；delete_file 类危险工具在无审批时不可执行。

M2可靠运行

SQLite 持久化 · 结构化事件 + 流式 · Provider 重试 / 降级 · 配置全量生效 · 核心测试集。
交付判据：杀进程重启后对话可续；模型断连自动恢复；核心链路有测试覆盖。

M3生产运营

上下文压缩 · 审批持久化 + 渐进信任 · OTel 可观测 · 特性门控 · benchmark 基线。
交付判据：千轮长会话稳定运行；全链路 trace 可查；审批记录可审计。

M4生态扩展

MCP 集成 · 任务编排 · 多智能体 · 插件体系 · 可写记忆。
交付判据：外部 MCP 工具可挂载且有权限门控；多步任务可编排。
