# 02 - 核心概念地图

10 个术语，读完就能看懂其余文档。每个术语给出：定义 → 例子 → 反例 → 一句话记住。

## 1. Harness

**定义**：把模型包在中间的那层工程外壳。它不产生智能，只负责循环、约束与状态：调用模型、校验工具、裁决权限、压缩上下文、持久化会话。

**例子**：`backend/mini_harness/` 整个包就是 Harness；`RuntimeEngine.run()` 是它的主循环。

**反例**：写在 `projects/` 里的业务工具、业务提示词，不属于 Harness，属于领域代码。

**一句话记住**：Harness 是"驾驶舱"，模型是"发动机"。

## 2. RuntimeEngine

**定义**：Harness 的唯一执行入口，Agent Loop 的实现类。它持有模型供应商、工具注册表、权限门控、Token 预算、上下文组装器与记忆，对外只暴露两个异步入口：`run()` 与 `resume()`。

**例子**：`RuntimeEngine.run("现在几点？")` 返回一个事件流；审批挂起后调 `resume()` 继续跑。

**反例**：不要在外层自己写"调模型 → 判断有没有 tool_calls → 再调模型"的循环，那会绕过校验、权限与预算。

**一句话记住**：引擎是"引擎"，你只递交订单（用户输入），不亲自开车。

## 3. Event

**定义**：引擎对外输出的类型化消息，也是引擎与前端/调用方之间的唯一契约。每个事件有 `type`、`data`、`session_id` 三个字段。

**例子**：`{"type": "tool_executed", "data": {"tool": "get_time", "ok": true, "result": "2026-09-23T..."}}`。

**反例**：不要靠解析模型输出的文本前缀（如 `TOOL:`）来获取状态——那正是本框架用事件取代的做法。

**一句话记住**：事件是"黑匣子录音"，全程可回放、可断言。

## 4. Turn

**定义**：一次"模型调用 + 该次调用产生的工具执行"，是一轮完整的推理步。引擎在 `max_turns` 内循环 Turn，直到模型不再要求调用工具。

**例子**：用户问"现在几点" → Turn 1 模型要求调用 `get_time` → 工具执行并回填 → Turn 2 模型据此给出回答。

**反例**：把"用户发一条消息"当成一个 Turn 是错的——一条消息常需要多个 Turn。

**一句话记住**：Turn 是"一问一答之间的一次呼吸"。

## 5. Tool

**定义**：模型可以调用的外部能力，由一个普通 Python 函数加 `@tool` 元数据声明。参数 JSON Schema 由函数签名自动生成，执行在带超时保护的工作线程里。

**例子**：`@tool(name="lookup_order", description="按订单号查询", permission=PermissionLevel.FULL_TRUST)` 装饰 `def lookup_order(order_id: str) -> str`。

**反例**：不要让工具返回非字符串的复杂对象，也不要让工具自己做审批——审批由权限门控统一裁决。

**一句话记住**：工具是"模型的手"，但手要经过护栏才能伸出去。

## 6. Hook

**定义**：插在引擎生命周期五个固定点上的回调，用于输入过滤、结果清洗、埋点。全部方法默认空实现，按配置的导入路径加载，同一点位按顺序链式执行。

**例子**：`after_tool_execute` 里把工具结果中的手机号打码，再写回账本（见 [05-build-a-project.md](05-build-a-project.md)）。

**反例**：不要在 Hook 里实现业务工具逻辑——Hook 是横切关注（脱敏、审计、限流），不该承担领域职责。

**一句话记住**：Hook 是"安检口"，不改引擎也能查包。

## 7. Provider

**定义**：模型供应商抽象（`BaseModelProvider`）。必须实现 `chat()` 与 `chat_stream()`：前者返回完整响应，后者按块产出增量文本与最终响应。

**例子**：`OpenAIProvider` 用 `AsyncOpenAI` 实现这两个方法，因此 DeepSeek、通义、Ollama 都能直接接入。

**反例**：不要在引擎或工具里直接 `import openai` —— 换成 Claude 时你会被迫改内核。

**一句话记住**：Provider 是"电源插头"，插座标准化了就能换电。

## 8. Memory

**定义**：记忆分两层。**会话账本**（`SessionStore`）保存某一次会话的全部消息、工具结果与摘要；**长期记忆**（`LongTermMemory`）跨会话保存事实与偏好，按关键词检索后注入上下文尾部。两者的存储后端都收口在持久化层。

**例子**：用户说"以后都用中文回答" → 模型调用 `memory_save` 写入长期记忆 → 新会话里通过 `memory_search` 或自动注入被召回。

**反例**：不要把长期记忆当成向量数据库用；当前实现是关键词重合度检索，语义召回需要替换后端。

**一句话记住**：会话账本是"今天的会议记录"，长期记忆是"这个人的档案"。

## 9. Session

**定义**：一次连续对话的标识（`session_id`）。引擎按其从数据库重建状态，因此进程重启、服务多实例、审批中断后再恢复，都不丢上下文。

**例子**：前端"新会话"按钮就是生成一个新的 `session_id`；`GET /api/sessions/{id}/messages` 能读回全部历史。

**反例**：不要把 `session_id` 当成用户 ID——同一个人可以有多个会话，长期记忆才是跨会话的部分。

**一句话记住**：Session 是"一条对话的时间线"。

## 10. ProjectConfig

**定义**：一个项目的全部配置（`ProjectConfig`），从 YAML 加载：身份、提示词路径、模型、记忆、预算、工具、权限、钩子、轮次上限。YAML 里留空或写 `null` 的字段会回填环境变量层的值。

**例子**：`projects/customer_service/config.yaml` 声明 `agent_name: 客服助手`、启用三个领域工具、加载脱敏钩子。

**反例**：不要把密钥写进 YAML；密钥属于环境变量层（`.env`），YAML 里写 `null` 即可。

**一句话记住**：ProjectConfig 是"项目身份证 + 说明书"。
